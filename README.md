# 临时聊天室 · wechat-ntr

一个仿微信聊天界面的、**无需注册 / 不加载历史消息 / 纯前端部署**的临时聊天室。

项目只有一个可直接部署的 `index.html`：浏览器通过公共 MQTT WebSocket 服务交换消息，聊天内容在发送前加密；图片和文件保持原始字节，按块传输，接收完成后通过 SHA-256 校验完整性。新版附件在双方支持时使用加密二进制消息，减少文本封装开销，并以小窗口、均匀发送的方式控制传输节奏。

> 这个项目更适合临时、低敏感度交流和前端实验。当前房间密钥由本地时间推导，**不应把它当作经过安全审计的私密通信工具**。传输优化不构成固定速度、稳定带宽或高安全等级的保证。

## 特性

- 微信风格的移动端优先聊天界面，分组展示会话说明
- 附件卡片集中展示大文件提醒、接收进度和传输状态，不增加模式开关或诊断面板
- 紧凑双列测速显示：传输速度与预计剩余时间；完成后显示平均速度与接收用时
- 无账号、无注册、无应用后端，单个 HTML 文件即可部署
- 按小时自动进入临时房间
- 文本消息通过 CryptoJS AES 加密后发送
- MQTT 断线自动重连，并明确展示连接状态
- 不加载历史消息；QoS 0，不使用 retained message
- 昵称只保存在当前标签页的 `sessionStorage`
- Enter 发送、Shift + Enter 换行，兼容中文输入法 composition
- 使用 DOM API / `textContent` 渲染用户内容，避免直接插入不可信 HTML
- 图片与文件均保持**原始字节不变**，不压缩、不降质
- 单个附件建议不超过 **5 MiB（约 5 MB）**，允许更大的文件
- 附件按 **8 KiB** 分块传输；支持缺块补传、暂停与继续接收
- 双方支持时使用原生 AES-GCM 加密的二进制分块，不支持时回退至兼容格式
- 二进制传输采用小窗口、均匀发送、温和调速和发送缓冲控制
- 接收后进行 **SHA-256** 完整性校验，通过后才开放下载
- PNG / JPEG / GIF / WebP 可在聊天中预览，下载仍为原始文件
- 不设固定附件大小或总字节数上限；实际容量受设备内存和浏览器限制

## 快速使用

1. 打开页面，输入昵称进入聊天室。
2. 双方在同一本地小时加入，并保持设备时间与时区一致。
3. 点击「＋」选择图片或文件；对方点击「接收原文件」开始传输。
4. 在文件卡片中查看进度、速度和预计剩余时间；需要时可暂停，再点击「继续接收」。
5. 保持双方页面在线，完整性校验通过后点击「下载原文件」保存。

**收发双方都刷新至新版，才能在能力允许时使用二进制传输。**新旧版本可以通过兼容路径传输，但不能体现完整的二进制减负效果。

附件建议不超过 **5 MiB**，更大的文件仍可传输。超过建议大小时，附件卡片会显示提醒，不会直接拒绝；实际传输能力取决于设备内存、浏览器、网络和公共消息服务。

## 工作原理

文本消息流程：

```text
浏览器 A
  │
  │  roomKey = 本地时间 YYYYMMDDHH
  │  topic   = chat/MD5(roomKey)
  │  payload = AES(JSON, roomKey)
  ▼
公共 MQTT Broker (WSS)
  │
  ▼
浏览器 B
```

文件同样经过公共 MQTT Broker 中转，**不是浏览器之间的直连，也不使用 WebRTC**。「纯前端」表示无需自行搭建业务后端、数据库或用户系统，并不表示没有第三方服务器参与。

当前 MQTT Broker：

```text
wss://broker.emqx.io:8084/mqtt
```

MQTT.js 固定使用 `5.10.4`，在浏览器中优先从 jsDelivr 动态加载，失败后尝试 unpkg。CryptoJS 已直接内联在 `index.html` 中；二进制附件使用浏览器原生 Web Crypto API。

### 房间规则

加入聊天室时，页面按设备的**本地年月日小时**生成：

```text
YYYYMMDDHH
```

例如本地时间为 2026-09-21 14:37，则房间时段为：

```text
2026092114
```

随后使用：

```text
chat/MD5(2026092114)
```

作为 MQTT topic，并使用同一个 `roomKey` 作为 CryptoJS AES 的 passphrase。

因此：

- 双方设备时间和时区需要一致，才能自动进入同一个房间。
- 跨小时后，已经加入的页面仍留在原房间。
- 退出后重新加入，才会进入新的小时房间。
- 断线重连仍回到加入时的房间。
- 断线期间的聊天消息不会补发。

## 附件传输

### 通知、分块与完整性校验

1. 发送端读取原始文件字节并计算 SHA-256，准备附件元信息。
2. 发送端先广播文件通知，不主动一次性推送整个文件。
3. 接收端点击「接收原文件」后，请求缺失分块。
4. 双方能力允许时采用二进制路径，否则采用兼容路径；每块原始数据为 8 KiB，末块可更小。
5. 接收端按分块编号重组原始字节，缺块时请求补传。
6. 全部分块收齐后重新计算 SHA-256，摘要一致时才提供「下载原文件」。
7. 接收端完成校验后向发送端发送回执；校验失败则提示重新接收，不把错误内容当成成功文件。

文件卡片出现只表示收到文件通知，不表示文件已经传完。本地 MQTT 写入成功也不等于对方已经接收；发送端的完成提示以接收端校验回执为依据。

### 二进制路径与兼容回退

文件通知、请求、取消和校验回执仍走原有控制 topic：

```text
<chat-topic>/files/v1
```

双方均支持时，附件内容通过接收者专属 topic 发送：

```text
<chat-topic>/files/v2/<接收者 senderId>
```

二进制分块采用 **AES-GCM** 加密，省去原来「分块 Base64 → JSON → 密文文本」的叠加包装。文件密钥使用房间键、随机盐和文件上下文，经 PBKDF2-SHA-256 导出；每个文件缓存一次导出结果，而不是逐块重复派生。每次发送使用新的随机 IV，最终仍做整文件 SHA-256 校验。

接收者专属 topic 用来减少无关的文件转发，**不是身份认证或访问控制机制**。

旧客户端参与、所需原生加密能力不可用、二进制订阅失败等情况下，使用原有 v1 加密文本格式。二进制路径开始后约 12 秒仍未收到有效二进制分块时，也会尝试回退。旧到仍有 5 MiB 硬限制的客户端，可能忽略更大的附件通知，因此仍建议双方更新。

### 发送节奏与使用边界

二进制路径固定保持少量分块在途，按接收反馈温和调整发送目标；分块均匀发出，不集中倾倒整个窗口。发送缓冲积压时暂停填充；超时退让设有恢复间隔，避免同一批缺块反复大幅降速。页面计时延迟后也不会通过大批突发发送来「追赶」进度。

| 项目 | 当前值 |
| --- | --- |
| 单个附件建议大小 | 不超过 5 MiB，超出仅提示，仍可传输 |
| 原始分块大小 | 8 KiB |
| 二进制在途窗口 | 最多 12 块，即 96 KiB 原始数据 |
| 每次控制请求 | 最多 4 个分块编号 |
| 页面附件内存 | 不设固定字节数上限，受设备内存和浏览器限制 |
| 同时保留的附件项 | 最多 40 个 |
| 图片预览 | PNG / JPEG / GIF / WebP |
| 传输要求 | 发送方与接收方需要同时在线 |

内部二进制发送目标从 64 KiB/s 起步，在 24～96 KiB/s 范围内调整。这些是**应用层调度参数，不是实测速度、带宽保底或性能承诺**。网络延迟、重传、公共服务负载、浏览器后台节流和设备休眠仍可能造成波动或中断。

大文件不会因为超过 5 MiB 或页面附件合计超过 30 MiB 而被硬性拒绝，但代码仍会在浏览器内存中保存完整文件，**不是无限容量或流式落盘**。建议及时移除不需要的附件以释放内存。

暂停或短暂断线后，只要双方相关页面、会话和附件缓存仍保留，可继续请求缺失分块。刷新、关闭页面、退出房间或移除附件后，不能保证恢复；没有供离线接收的云端文件副本。

附件不会压缩、缩放或重新编码。文件系统层面的创建时间、下载时间等属性可能变化，但下载内容的字节应与发送前一致；页面使用 SHA-256 对这一点进行校验。

### 速度与剩余时间显示

接收中的文件卡片以双列显示「传输速度」和「预计剩余」；速度数值、单位与说明分层呈现，数字采用等宽排版。完成后，同一位置显示「平均速度」和「接收用时」。暂停、连接中断和末尾校验期间会收起测速区域，避免保留过时的倒计时。

统计口径：

- 实时速度使用约 **3 秒滑动窗口**，每 **500 毫秒**更新显示。
- 只统计实际收到且去重后的原文件字节，不把重复分块或协议包装算成有效文件速度。
- 单位为 **KiB/s / MiB/s**，分别按 1024 / 1048576 字节换算。
- 剩余时间根据当前有效速度估算；开始时显示计算中，没有有效进展时显示等待数据，不是固定完成时间。
- 完成后的平均速度与接收用时按累计接收活动时间计算，排除暂停、中断后等待继续及末尾校验的时间；不等同于从第一次点击接收到校验完成的全程耗时。

测速是独立的显示模块，不用显示数字来驱动发送调度。对照测试应使用同一文件、相同设备和网络，先保持两端页面可见；同时记录全程耗时，不以某一瞬间的峰值判断效果。

## 安全与隐私说明

这个项目有加密，但当前设计的目标是「临时聊天实验」，而不是高安全等级通信。

需要特别注意：

- 房间密钥直接由 `YYYYMMDDHH` 推导，可预测。
- MQTT topic 也由同一时间值计算，因此了解实现的人可以枚举对应时段的房间。
- 没有账号体系、成员认证或可信身份校验，昵称不能证明真实身份。
- 当前消息没有额外的发送者身份签名机制。
- 新增 AES-GCM 和密钥派生不会把可预测的房间键变成秘密，也不提供可信成员身份或前向保密。
- SHA-256 用于检测文件内容是否一致，不验证发送者身份，也不是文件安全扫描。
- 使用的是公共 MQTT Broker，服务可用性、流量限制、日志及运营策略不由本项目控制。
- 项目没有经过正式的密码学或安全审计。

因此，请不要通过本项目发送密码、密钥、身份证件、财务资料、商业机密或其他高敏感信息。

安全问题反馈方式见 [SECURITY.md](SECURITY.md)。

## 本地运行

这是纯静态项目，没有构建步骤。

最简单的方式是直接打开 `index.html`。如果浏览器或安全策略限制本地文件加载，也可以启动任意静态 HTTP 服务，例如：

```bash
python -m http.server 8080
```

然后访问：

```text
http://localhost:8080/
```

二进制路径取决于浏览器是否提供所需原生加密能力；能力不足时会回退，不影响兼容路径。公开部署建议使用 HTTPS 静态站点。直接打开本地文件也仍需联网加载 MQTT.js 并连接公共 Broker。

## 部署到 Cloudflare Pages

仓库本身就是可部署产物，不需要编译。

如果 Cloudflare Pages 已连接这个 GitHub 仓库：

1. 将生产分支设为 `main`。
2. 不需要构建命令。
3. 让部署结果直接使用仓库根目录中的 `index.html`。
4. 后续向 `main` push 后，由已配置的自动部署流程创建新部署；以托管平台显示的实际部署状态为准。

如果使用其他静态托管服务，同样只需要把仓库根目录作为站点目录发布。部署完成后，收发双方都应刷新页面。

## 开发约定

当前项目刻意保持「单文件部署」的形态。修改时建议继续保持：

- 不引入必须运行的业务后端服务。
- 不把用户消息直接写入 `innerHTML`。
- 修改房间密钥、topic、消息 JSON 或附件协议时考虑旧版本兼容与能力回退。
- 附件下载前必须先完成完整性校验，不为追求速度跳过校验或改写原文件。
- 发送成功与「对方已经收到」是两个不同概念；不要仅凭本地 socket 写入就显示已送达。
- 保持测速展示与传输调度分离，修改显示样式不应改变计时口径或传输参数。

贡献流程见 [CONTRIBUTING.md](CONTRIBUTING.md)。
